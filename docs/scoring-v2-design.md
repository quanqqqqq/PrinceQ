# PrinceQ 动态评分方案 v2

状态：设计方案。2026-10-14 本轮落地了助手与 Skill 的评分指导及默认注入；下述确定性评分引擎、动态视图、日历与剩余工时字段尚未实现。没有改变现有任务、目标、已确认评分或排序公式。

## 1. 当前实现审视

| 范围 | 当前实现 | 影响 |
|---|---|---|
| 队列截止压力 | 超期/24 小时/3 天/7 天/30 天固定阶梯；没期限为 0.35 | 临界点跳变；同期限不同工作量同分；无期限可能超过远期限 |
| 任务分布视图 | 保存的 importance/urgency 两轴分数 | 时间流逝或任务插入不会自动刷新两轴 |
| 队列主排序 | 截止、人工优先、依赖、耗时、习惯、连续性六因素 | 两轴重要度不直接参与；小任务的耗时加分可能压过重要长任务 |
| 队列读取 | 使用最新持久化快照；无快照时读取会生成快照 | 即使工作事实不变，时间压力也可能过时 |
| 助手上下文 | 每轮在内存重新算队列 | UI 快照与助手即时分数可能不一致 |
| 依赖因素 | 按直接阻塞数量加分，受阻减分 | 不知道解锁成果的价值、期限或完整链路 |
| 本地象限建议 | 关键词、类型、认知负荷、总估时、目标关联加减分 | 工时长或深度工作不天然等于重要；关键词也不能证明收益 |
| 日历事实 | 换算系数、偏好时段、文本/结构约束 | 缺少实际工作日、忙闲日历、剩余工时、目标价值与延期损失 |

定位：server/domain/queue.ts、quadrant.ts、matrix-score.ts、server/repo/queue-service.ts、server/agent/prompt-context.ts。

## 2. 三层语义和职责

1. 基础重要度 I_base：收益、失败后果、责任、战略贡献；人工或 Agent 有依据地判断，存为确认基线。
2. 当前评估 I_current / U_current：考虑有效目标、依赖、风险和时间变化的只读派生结果，标出来源和数据缺口。
3. 执行优先级 P：在能够开始且满足工作约束的行动中选择下一步。不是两轴任一分数，也不是简单的任务时长倒数。

重要度用绝对锚点，避免当前任务最大最小值或百分位归一化；否则插入一件高分任务会让所有原有分数变低。排序是相对的，分数含义应稳定。0..100 是方便比较的产品刻度，不是成功/违约概率，也不保证两件分数相差 10 就存在等比例价值差。

Agent 负责从描述、目标和责任提议语义判断；确定性程序负责时间、单位、依赖、资源与排序计算。不要让模型每分钟重新给所有任务随意打分。

## 3. 紧急度：从距离截止到时间余量

基本概念：
- A(t,d)：当前至有效截止之间，已知可供相应执行人使用的工作分钟。
- R(t)：当前剩余工作分钟；总 estimated_minutes 只能是注明假设的退化近似。
- B：必要人工工时缓冲；需要来源，不使用假装科学的固定概率。
- W：明确的外部等待、释放时间和交接；在日历时间轴放置，不能把等待分钟机械扣为工作分钟。
- 单项任务无依赖等待时，S = A(t,d) − R(t) − B。
- 有依赖、等待或不可拆分工作块时，通过可行日程得到最晚开始时间/完成时间和余量，而不是只套这个减法。

在其他事实不变时，A 随时间不增加，S 不增加，U 应不下降。完成部分工作、截止延长、人员/资源增多、风险解除时可以下降。无实际可用日历时，日历剩余时长至多作为容量上界；不能用“每日 8 小时换算”冒充实际已知的空闲时间。高峰时段作为适配偏好，禁止时段才作为硬限制。

### 3.1 连续刻度的候选方案

相比截止日阶梯，余量曲线在各个点之间连续插值，消除临界点跳变。定义 q = S / max(R+B, 已知最小有效工作块)。需要这些量已知且 R>0；缺少事实输出未知或范围，不默填零。

可供首轮校准的锚点：

| q | 候选 U | 解释 |
|---|---|---|
| >= 3 | 10 | 可容纳约三份额外工作余量 |
| 1 | 30 | 尚有一份额外工作余量 |
| 0.25 | 55 | 余量较窄 |
| 0 | 75 | 几乎没有缓冲，到了最晚开始边界 |
| -0.5 | 90 | 已需调整范围、资源或期限 |
| <= -1 | 100 | 当前假设下显著无法按期完成 |

这些数值是 PrinceQ 候选产品参数，不是调度理论规定的数字；未经真实数据回放不能宣称更精准。该曲线本身不判断剩余机会窗口、持续故障损失或硬截止过期后的价值。额外事件分别显示，明确严重故障可进入事件响应类别。不要用取最大值后重复在队列里给同一个损失再加几次分。

### 3.2 正常、未知、失效三种状态

- 无自身截止但有真实下游硬截止：从下游交付反推前置最晚完成；不用伪造自己的 deadline。
- 无任何时间/损失证据：时间压力未知；不要同时假定“没有期限所以低分”和“默认 0.35 所以比远期限更急”。
- 已过期：仍有延期损失/仍有交付价值则保持高压；机会已永久失效则提示重议、取消或归档，修改待确认。
- 估时未知：优先提示风险与范围，不把剩余工时按零计算。
- 缺实际日历：按明确假设展示可用时间区间，可用上下界分别计算风险；只有上下界跨越决策边界且影响安排时追问。
- 仅日期 deadline：必须统一产品时区与“当天结束”的业务语义；当前未迁移旧数据，不自行把已有时间戳移动到当地午夜。

## 4. 任务插入与依赖网络

### 4.1 新增一个无关任务

旧任务基础重要度不动。若明确分配到同一个人且截止冲突，新任务消耗可用容量，旧任务完成风险/优先级可能改变。仅把所有任务工时累加到每个任务上会重复扣容量；应进行一次资源可行的日程计算，保留每份工作块唯一归属。不同执行人、未领取任务和用户个人队列的承担范围必须显式区分。

### 4.2 新交付依赖一个旧任务

旧任务的解锁价值提高，且承接下游的最晚完成时间。例如“更新说明”变为“重要上线必须先通过说明审核”，当前重要度可以提升；原始价值基线保留，展示变化依据。删除依赖、完成交付、目标暂停/放弃后派生提升应相应消失。

只使用已确认的依赖边；从描述猜到的依赖先给预览，不能当成事实参与持久化。遍历有效未完成下游，对同一成果去重；共享前置/分支不重复加钱。目标链接仅证明关联，不足以证明“全部任务都是交付必要项”或全部继承目标日期。

### 4.3 依赖计算

先校验 DAG 与边的有效状态。从明确交付里程碑反推最晚时间，结合执行者资源和等待事实。如果一个人执行多条分支，不能用最长路径假设并行；如果独立执行人可并行，关键路径仍只给依赖层面的下界，资源冲突需另算。未知资源/等待时显示“不足以判定”，不输出伪精确的关键路径日期。

本期业务会把 completed/archived 视为依赖满足；v2 必须明确复用这一现有语义还是另作调整，不能悄悄把归档解释为实际完成。若提出新语义，需要独立迁移与确认。

## 5. 重要度如何动态变化

基础判断使用 Skill 中的绝对锚点，按目标贡献、收益规模、失败后果和责任给出建议。避免“耗时越长、工作越难、标题写着战略、任务关联目标越多，所以越重要”。

派生解锁价值可用一条保守规则表达：
I_current = max(I_base, 各个已知下游成果的必要性 × 该成果的重要度)。
这是候选语义，不是已上线公式。必要性须有依据，确认的不可替代前置可以接近 1，替代手段或不明确的关系须降低或标记未知；不能随意编造小数。max 去重可限制依赖数量膨胀；多个独立成果的总价值要有同尺度事实后才合并，不能拿轴分数当金额求和。

用户已确认的 I_base 不在读取时改写。目标方向、收益或风险变了，可以提示复评；只读计算不把未经确认的新语义当成已确认字段。人工明确固定当前分数时，保留固定模式，提示模型计算结果与人工值差异；自动模式需要明确可见，不能在后台忽略用户手动数值。

## 6. 如何形成执行队列

| 方法 | 优点 | 局限 |
|---|---|---|
| 最早截止优先 | 简单可解释 | 忽略剩余工时与价值 |
| 最小余量优先 | 长任务可以提前暴露风险 | 估时/日历错误会影响结果，也可能偏爱低价值急事 |
| 单位延期损失/交付收益 | 可以保住高价值成果 | 需要有依据且可比的价值判断 |
| PrinceQ 混合方式 | 先处理可行性与关键风险，再兼顾目标价值 | 必须公开假设、防止重复计算同一影响 |

建议管道：
1. 剔除已完成/归档工作；区分能执行、等待依赖、外部受阻。受阻任务在“等待与阻塞”中可见，但“下一件可执行工作”返回解除阻塞行动或真实就绪前置。
2. 对硬截止承诺作资源可行性评估。不可行时先给出冲突和可确认的调整方案，不把所有工作都排成“马上做”。
3. 以目标收益、延误代价和余量作为主信号；I、U 保持可解释，避免“低价值无限逾期小事压过高价值长任务”。
4. 习惯、上下文连续性、当前可用时间块用于相近候选的选择；快任务奖励设上限。高价值长期工作安排持续工作块，避免长期饥饿；等待久也不能自动把低价值事变重要。
5. 人工优先调整有明显标记；调序不等同于更改重要度。展示关键原因：如“前置审核还需 2h，周五交付依赖它”；不用展示内部推理。
6. 相同输入/时点给相同结果，稳定任务 ID 为最终平局条件。使用适度稳定区间避免队列每分钟抖动；跨越最晚开始/紧急风险边界则立即更新。具体容差和权重待回放校准。

不急于选择没有数据支持的新权重。先产生可信的 I、U、准备状态和风险；如果旧六项权重迁移到新模型，需版本化和可比较的预览，不把旧设置数值强行套进含义不同的新因子。

## 7. 数据与界面

采用最少必要输入，优先使用已有事实和自然语言确认：
- 已有：任务截止、总估时、状态、执行者、依赖、目标与个人习惯。
- 渐进新增：剩余工时（明确与估计区分）、截止性质/交付是否仍有效、可用工作日与忙闲时段、目标/责任影响、明确等待时间与必要缓冲。
- 不要求用户登记任务时填完这些字段。信息缺失时显示范围/暂定；影响“今天先做什么”才询问关键问题。
- 保留 matrix_* 确认基线与版本，新增独立 current_assessment，包括两轴范围/来源/假设/计算时间/input_revision，不把派生值混回基础字段。
- 任务分布视图若展示动态轴，提供“当前评估/已确认基线”清楚的可见区别；未知用待评估，不放到低分角落。象限转换提示原因，不显示私有判定过程。
- 卡片默认一条理由、一个风险状态，需要时展开依据。示例：“还需约 6h；可安排 8h；缓冲 1h；余量约 1h”。

## 8. 更新、确认和工程顺序

读取应在内存派生分数，不改任务版本、不写操作日志、不生成数据库快照。显式确认业务变更才保存基线、任务字段与正式排序快照。

统一同一 assessment 服务供 UI、助手、外部 Skill 使用；任务/目标/依赖/设置改变时失效缓存，时间变化时每分钟或关键时点重算。页面可见时局部轮询/事件更新，无整页刷新；持久化快照是历史，不再等同于当前即时评估。

确认预览绑定事实版本和算法版本；时间独立变化不伪造成任务业务变更。若预览涉及具体日期安排，需短期有效并在确认前重新检查日程可行性，展示已变化的风险或重新预览。不能把已经同意的一份计划自动替换成另一个方案。

工程顺序：统一只读 assessment 与来源元数据 → 连续时间压力和未知处理 → 剩余工时/工作日历 → 依赖传播与资源可行性 → UI 与助手一致刷新 → 历史回放调参。各步独立上线且显示能力范围。完整动态引擎未完成时，助手仅按本轮指导给建议。

## 9. 后续验证标准（本轮未执行）

不在真实数据库造任务。隔离数据应覆盖：
- 固定工作量，时间推进，U 不下降；实际推进减少 R 后允许下降。
- 相同期限，长短任务不同余量；工作日、跨午夜、日期时区、会议、非连续块。
- 无期限但有下游交付；未知工时/日历不得默判安全。
- 无关插入不改 I_base；同人竞争只改变容量风险；新确认依赖提高解锁价值，删除/完成后消失。
- 共享前置、AND 分支、同人顺序与跨人并行、暂停目标、失效期限。
- 受阻任务不作为可直接开始动作；不绕过预览确认，不在 GET 写库。
- 同一时点 UI/助手/Skill 一致；不刷新整页，不修改人工基线。
- 长期重要任务不被无限小任务饿死；多个不可同时完成的承诺明确报冲突。
- 权重/锚点用独立历史回放评估误报、漏报、截止兑现和用户改序率；不能用“样例排序好看”声称模型精准。

## 10. 理论参考及边界

- [CMU 托管的 TimeSys 实时系统手册](https://course.ece.cmu.edu/~ece749/docs/RTSHandbook.pdf)：动态优先级与余量的概念参考。软件调度模型通常有比个人工作更明确的执行时长与资源假设，不能直接承诺在人类工作中保证最优。
- [PMI：A Schedule as a Valid and Dynamic Model](https://www.pmi.org/learning/library/schedule-valid-dynamic-model-7506)：依赖、资源和持续修订剩余工作是动态日程的重要输入。
- [PMI：Critical path method calculations](https://www.pmi.org/learning/library/2019/04/07/15/39/critical-path-method-calculations-scheduling-8040)：依赖路径与浮动时间的概念参考。

本方案的三层语义、重要度锚点、曲线候选数值、UI/确认策略是 PrinceQ 的产品设计判断，并非上述来源已经证明的算法。尚无实际工作日历和剩余工时数据，不能承诺“尽可能精准”已经得到实证验证。
